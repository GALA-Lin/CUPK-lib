### 第五章：运输层 深度复习总结

#### 1. 运输层概述

**地位与功能：**

>[!warning]
>  * 运输层是**唯一**负责**端到端**（即应用进程之间）通信的层次。
> * **网络层** 负责主机到主机通信，**运输层** 负责进程到进程通信。
> * 运输层有两种主要的协议：**TCP** 和 **UDP**。
>

**端口 (Port) 的概念 [必考]：**
* **作用：** 标识一台主机上的**应用进程**。
* **软件端口：** 是操作系统中进程与进程通信的抽象接口。
* **端口号：** 16 位整数，范围 0~65535。
    * **熟知端口 (Well-known Ports) (0~1023)：** 预先定义，用于最常用的服务器程序（如 HTTP: 80, DNS: 53, FTP: 20/21, SMTP: 25）。
    * **登记端口 (Registered Ports) (1024~49151)：** 为没有熟知端口的应用程序保留。
    * **临时端口/动态端口 (49152~65535)：** 客户进程通信时临时分配。
* **套接字 (Socket)：** 标识主机上某一应用进程的唯一标识。
    $$\text{Socket} = (\text{IP 地址} + \text{端口号})$$

#### 2. 用户数据报协议 UDP

**特点 (四个“不”) [必背]：**
1.  **无连接：** 发送前不需要建立连接，传输结束不需要释放连接。
2.  **不可靠：** 尽最大努力交付，不保证可靠性。
3.  **面向报文：** 应用程序交给 UDP 的数据报文，UDP **不合并也不拆分**，直接添加首部转发。
4.  **无拥塞控制、无流量控制。**

**适用场景：**

* 对实时性要求高，允许少量丢失的应用（如 DNS、视频会议、IP 电话）。

**UDP 首部格式：**
* **固定 8 字节**（源端口、目的端口、长度、校验和，各 2 字节）。
* **校验和：** UDP 校验和是可选的（但 IPv4 中通常使用），覆盖 **UDP 伪首部**、UDP 首部和数据。

#### 3. 传输控制协议 TCP

**特点 (四大特性) [必背]：**
1.  **面向连接：** 必须先建立连接，后通信，最后释放连接。
2.  **可靠传输：** 使用**序号、确认、重传机制**保证数据不丢失、不重复、不失序。
3.  **面向字节流：** TCP 把上层数据看作一串**无结构的字节流**，会根据需要拆分或合并发送。
4.  **全双工通信：** 双方可以同时发送和接收数据。

**TCP 报文段首部格式  [必考关键字段]：**

![image-20251213003124457](E:\CUPK-lib\计算机网络\Review\5章.assets\image-20251213003124457.png)

* **序号 (Sequence Number, SN)：** 占 4 字节。当前报文段**第一个数据字节**的序号。
* **确认号 (Acknowledgment Number, AN)：** 占 4 字节。期望**下次收到对方的第一个数据字节**的序号（$\text{确认号} = \text{已收到的最后一个数据字节的序号} + 1$）。
* **数据偏移 (Data Offset)：** 占 4 位。指出 TCP 首部长度，单位是 **4 字节**。
* **窗口 (Window)：** 占 2 字节。告诉对方**目前可接收的数据量**（流量控制）。
* **标志位 (Flags) [重点]：**
    * **ACK (确认)：** 只有当 ACK=1 时，确认号字段才有效。
    * **SYN (同步)：** 用于**建立连接**。SYN=1, ACK=0 表示连接请求；SYN=1, ACK=1 表示同意连接。
    * **FIN (终止)：** 用于**释放连接**。FIN=1 表示数据已发送完毕，要求释放连接。
    * **RST (复位)：** 连接出现严重差错，必须释放连接。
    * **URG (紧急)：** 紧急指针字段有效。
    * **PSH (推送)：** 立即创建推送操作。

#### 4. TCP 的可靠传输实现

* **停止等待协议：** 每发送一个分组就等待确认，收到确认再发下一个。效率低。
* **连续 ARQ 协议 (滑动窗口协议)：** 发送方维持一个**发送窗口**，可连续发送多个分组。
    * **确认机制：** **累计确认**（只确认已收到的最后一个按序数据）。
    * **重传机制：** **超时重传**（等待时间到）或**快速重传**（收到 3 个重复确认）。

#### 5. TCP 的流量控制 (Flow Control)

* **目的：** 控制发送方速率，防止**接收方**的缓冲区溢出。
* **机制：** 利用 TCP 首部中的 **窗口字段**。
    * 接收方通过将自己当前的**接收窗口 (Rwnd)** 大小填入报文段的窗口字段，通知发送方最多可以发送多少字节的数据。
    * 发送方的**发送窗口**大小始终受 **接收窗口 (Rwnd)** 和 **拥塞窗口 (Cwnd)** 的较小值限制。

#### 6. TCP 的拥塞控制 (Congestion Control)  [必考原理]

* **目的：** 防止**网络**出现拥塞，是全局性的控制。
* **机制：** 发送方维护一个**拥塞窗口 (Cwnd)**。拥塞控制的四个阶段：
    1.  **慢开始 (Slow Start)：**
        * 连接刚建立或发生超时重传时。
        * **Cwnd 初始值较小，每收到一个 ACK，Cwnd 加 1 MSS** (指数增长)。
        * 增长到**慢开始门限 (SSTHRESH)** 时，进入拥塞避免。
    2.  **拥塞避免 (Congestion Avoidance)：**
        * **每经过一个 RTT**（收到一轮 ACK），**Cwnd 加 1 MSS** (线性增长)。
        * 直到网络发生拥塞。
    3.  **快重传 (Fast Retransmit)：**
        * 收到 **3 个重复确认** (Triple Duplicate ACK) 时，认为只是轻微拥塞，**不等待超时** 立即重传。
        * **SSTHRESH 减半**，进入**快恢复**。
    4.  **快恢复 (Fast Recovery)：**
        * 执行快重传后进入。
        * **Cwnd = 新的 SSTHRESH + 3 MSS** (因为收到了 3 个重复 ACK)。
        * 然后开始**线性增长**（类似拥塞避免）。
* **超时重传** 发生时：SSTHRESH 减半，Cwnd 设为 1 MSS，重新进入**慢开始**。

#### 7. TCP 的连接管理 

**1. 连接的建立——三报文握手 (Three-Way Handshake) [必考]：**

| 步骤        | 发送方 $\to$ 接收方       | 接收方 $\to$ 发送方            | 目的/状态变化                                             |
| :---------- | :------------------------ | :----------------------------- | :-------------------------------------------------------- |
| **1. 请求** | `SYN=1, Seq=x`            |                                | 客户端 $\to$ 服务器：请求连接 (状态 $\mathbf{SYN\_SENT}$) |
| **2. 确认** |                           | `SYN=1, ACK=1, Seq=y, Ack=x+1` | 服务器 $\to$ 客户端：同意连接 (状态 $\mathbf{SYN\_RCVD}$) |
| **3. 建立** | `ACK=1, Seq=x+1, Ack=y+1` |                                | 客户端 $\to$ 服务器：确认 (状态 $\mathbf{ESTABLISHED}$)   |

**2. 连接的释放——四报文挥手 (Four-Way Wavehand) [必考]：**

| 步骤            | 发送方 $\to$ 接收方 | 接收方 $\to$ 发送方            | 目的/状态变化                                                |
| :-------------- | :------------------ | :----------------------------- | :----------------------------------------------------------- |
| **1. 关闭请求** | `FIN=1, Seq=u`      |                                | 主动方 $\to$ 被动方：我要关闭了 (状态 $\mathbf{FIN\_WAIT\_1}$) |
| **2. 确认接收** |                     | `ACK=1, Ack=u+1`               | 被动方 $\to$ 主动方：确认收到关闭请求 (状态 $\mathbf{CLOSE\_WAIT}$) |
| **3. 最终关闭** |                     | `FIN=1, ACK=1, Seq=w, Ack=u+1` | 被动方 $\to$ 主动方：我也关闭了 (状态 $\mathbf{LAST\_ACK}$)  |
| **4. 确认关闭** | `ACK=1, Ack=w+1`    |                                | 主动方 $\to$ 被动方：最终确认 (状态 $\mathbf{TIME\_WAIT}$)   |

* **等待 2MSL (Maximum Segment Lifetime)：** 主动关闭方进入 $\mathbf{TIME\_WAIT}$ 状态后，必须等待 $2 \times \text{MSL}$ 时间，确保最后一个 ACK 报文段已送达对方，并防止延迟的报文段干扰新的连接。
